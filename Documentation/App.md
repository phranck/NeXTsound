# Native workbench

NeXTsound is a SwiftUI app for macOS 26 and later. Its main window is the front panel, which shows the Library panel as a sheet, and it manages a local profile library. It discovers compatible SoundBoxes and shows their connection status, custom name, and firmware version through a read-only capabilities query, can write a new persisted name to the board, mirrors every profile edit to the board automatically for live listening, and saves the current profile on the board when asked to. A mirrored edit lives only in the board's memory, so a reconnect or power cycle reverts to the board's last saved DSP state. No write resets the board or changes the system audio output. Generation-aware negotiation and retries remain tracked in [issue 16](https://github.com/phranck/NeXTsound/issues/16).

## Build

From the repository root:

```bash
bash Scripts/app.sh
```

The command selects the Xcode version from `toolchain.json`, bootstraps the checksum-pinned XcodeGen, generates `App/NeXTsound.xcodeproj`, and builds Debug and Release without signing. It does not launch or install the app.

Build products:

- `.build/macOS/Build/Products/Debug/NeXTsound.app`
- `.build/macOS/Build/Products/Release/NeXTsound.app`

The complete repository gate is `bash Scripts/check.sh`. It includes shared and app package tests, formatting/lint, Release packages, all RP2350 targets and guards, and both native app configurations.

## Front panel

The front panel is the app's main window (`Window(id: WorkbenchLayout.frontPanelWindowID)`), and closing it quits the app. Its brushed metal reaches under the hidden title bar, and the window takes the size of the panel. A drag anywhere on the panel moves the window, unless it starts on a control.

The multifunction display under the header plots the selected profile's response from the five EQ bands and, while it is enabled, the high-pass. The plot uses the shared DSP coefficients. It leaves out attenuation, mute and the limiter, so it is not an acoustic measurement, and it clips the curve at its labeled range without changing the settings. The profile's name stands under the curve. The status column at the right shows the SoundBox's connection, and for a verified board its name, serial, firmware, audio format, flash size with the storage state, and live values. The latest message stands on its bottom line.

The row of controls under the display edits the selected profile. The band panel's three sliders set the band that its five keys select, and the Edit menu and each band key's context menu enable or reset a band. The high-pass, output and sample-peak limiter modules hold the other sliders, the toggles for the high-pass and for mute, and the SAVE and FLASH buttons described below. The keys at the right end choose the displays' color, which the app keeps across launches. Under them, the LIBRARY key shows the Library panel as a sheet and stays down with its LED lit until the sheet closes. A slider follows the arrow keys, Page Up, Page Down, Home and End, and the frequency, quality and release sliders give every decade the same travel. Every edit registers its undo, is saved, and plays on a connected SoundBox.

## Profile library

`ProfileLibrary` is the internally managed collection of profiles; `ProfileLibraryStore` persists it as validated atomic local JSON under Application Support, independent of any file the user opens or saves. `ProfileFile` wraps the existing `SoundProfile` for exactly one purpose: it is the `FileDocument` adapter behind SwiftUI's `fileImporter`/`fileExporter`, so a profile's canonical validated JSON can be imported or exported explicitly. The native file extension is `.nxsprofile`; JSON profiles can also be imported. The app owns the exported `.nxsprofile` UTI but is not registered as a document editor for it or for generic JSON, since neither drives the app's lifecycle.

`WorkbenchModel` is the single `@Observable` source of truth: it owns the library, mediates every mutation through validation, registers native undo via the window's `UndoManager`, and debounces persistence. A failed load never blocks editing or quitting; it surfaces on the display's message line while edits continue in memory until storage recovers.

Two volatile A/B slots hold a captured `DSPSettings` snapshot each, for comparing variations during a single editing session. Capture copies the current profile's DSP settings into a slot; recall replaces only the current profile's DSP settings with a slot's capture, through the same validated edit transaction as any other change, so it advances the revision and supports undo. Neither slot is serialized, included in the saved library, or sent to a connected SoundBox on its own; they exist only in memory and are lost when the app quits. This is model-layer only for now; neither panel has A/B controls.

## Driver library

`DriverRecord` is a driver model entry the owner maintains by hand: Thiele/Small, electrical, mechanical, thermal, and dimensional parameters, a name/manufacturer, and an optional source. Missing parameters stay `nil` rather than defaulted. `DriverLibrary` is the validated collection, seeded by default with `DriverLibrary.knownCandidates`: the driver currently in use (Tectonic Elements TEBM28C10-4) plus researched candidates within the enclosure's size and depth envelope (Tectonic TEBM28C10-4B and -4BE, Dayton Audio CE41N-4, Visaton FR 58 in 4Ω and 8Ω, Visaton BF 37 in 4Ω and 8Ω). Each candidate's fields come only from its own manufacturer datasheet; a field stays `nil` where that datasheet does not give it directly, rather than computed from related fields or taken from a third-party aggregation that cannot be checked against the manufacturer's own source. `DriverLibraryStore` persists the library as atomic local JSON under Application Support, the same pattern `ProfileLibraryStore` uses (both now share the bounded atomic read/write in `AtomicJSONFile`); `DriverLibraryModel.start()` merges any known candidate not yet present (by id) into an already-persisted library, so a library saved before a new candidate was researched picks it up on the next launch. `DriverLibraryModel` is the `@Observable` CRUD state behind the Library panel's DRIVER MODELS key, which opens it in its own window (`Window(id: WorkbenchLayout.driverLibraryWindowID)`) rather than a sheet, so it stays open alongside the main window; it holds no reference to `BoardMonitor` or any board transport, so adding, editing, or removing a driver model never writes to a connected board. A selected entry's parameters are copied into a profile's `SpeakerRecord` snapshot rather than referenced live, matching the existing catalog/snapshot separation; the DSP calculation that reads a selected entry is [issue 19](https://github.com/phranck/NeXTsound/issues/19)'s own work.

An accepted edit advances the profile revision atomically. Failed edits and exhausted revisions leave the library unchanged. An incomplete name can remain in the library but fails validation on export. A new profile always starts flat and digitally muted (`FactoryPreset.flat`, the same settings a default `DSPSettings()` already produces); there is no starting preset to choose, since the owner builds every real profile by hand. `FactoryPreset`'s other cases (`warm`, `speech`) remain fixture data for the offscreen renderer and for tests, not a feature exposed in the app. The driver form's focus is its Thiele/Small, electrical, mechanical, and mounting parameters; a candidate researched from a manufacturer datasheet shows that datasheet as a clickable "Datasheet" link (its first `sourceURL`) rather than a bundled image or 3D model.

## Library panel

The Library panel is a sheet on the main window, which the front panel's LIBRARY key and the View menu's Show Library open. Its Profiles, Speaker and SoundBox sections stand side by side, each as wide as the four profile keys. The CLOSE key at its bottom right closes it and releases the LIBRARY key. Escape does not close the sheet, because a key bound to Escape would take Escape before a rename does. While the sheet is shown, the import and export panels open over it. Its sections follow the front panel's style, and its readouts take the display color that the front panel's keys choose.

The Profiles section lists the library's profiles on seven lines and marks the selected one. A click or the arrow keys select a profile. A double click or Return renames it in place, with a blinking cursor at the caret, and the typing goes to an invisible AppKit text field whose delegate sees Return and Escape before the panel does. Return or a click elsewhere keeps the new name, and Escape keeps the old one. The NEW, DELETE, IMPORT and EXPORT keys add, delete, import and export a profile, and the File menu offers the same as New Profile (⌘N), Delete Profile, Import Profile… (⌘O) and Export Profile… (⇧⌘E). The last profile cannot be deleted.

The Speaker section shows the selected profile's speaker on two lines. A click, Space, Return or the down arrow opens the native menu of every driver model over the readout. The amber SAFETY UNVERIFIED LED stays lit, because the speaker's safety margins are not established (see [issue 3](https://github.com/phranck/NeXTsound/issues/3)). Its caption's capitals start level with the top of the DRIVER MODELS key beside it, which opens the Driver Models window.

The SoundBox section shows the verified board's name on two lines, broken between its words as the speaker's name is, or No SoundBox and Not verified otherwise. The CONNECTED LED stands at the right end of the section's title, on its baseline, with its caption to its left. It is lit while a board is verified, and only then does the RENAME key under the readout open the rename form.

## Localization

The app is localized into English (development language) and German. Three String Catalogs carry the translations: `App/Application/InfoPlist.xcstrings` for the bundle name and the exported document type's description, `NeXTsoundWorkbench`'s own `Resources/Localizable.xcstrings` for every UI string of the app's windows, and `NeXTsoundCore`'s own `Resources/Localizable.xcstrings` for the shared model's validation and factory-preset strings. Each Swift package declares `defaultLocalization: "en"` and ships its catalog as a processed resource, so `Text`/`Button`/`.help(...)` literals resolve through the package's own resource bundle rather than the app's.

A `LocalizedError.errorDescription` or any other computed `String` built from a literal is not picked up by Xcode's source scanner on its own; each one is wrapped in `String(localized:)` so it participates in the catalog. `WireError`'s message is the one deliberate exception: it comes from the shared C protocol library's `nxs_result_description`, a wire-protocol debug string compiled into firmware and host alike, and stays English-only rather than duplicating a translation table across the Swift/C boundary.

Each button in the Driver Models window's toolbar has a `.help(...)` tooltip, translated alongside its label.

## Board discovery

`BoardMonitor` tracks one `BoardConnectionState`: disconnected, detected (matched by USB identity, not yet verified), verified (with the firmware's reported `DeviceCapabilities`), or mismatched (an invalid reply or a reported serial that disagrees with the enumerated device). `IOHIDBoardDiscovery` finds compatible boards through `IOHIDManager`, matching the canonical vendor/product ID and HID usage from `BoardIdentity`, without seizing the device. `USBHostBoardTransport` exchanges feature reports as raw USB class control transfers and validates each reply's identity, operation, and size before decoding it. It sends the capabilities and status requests, which change nothing, and the apply, rename, and save writes described below; it never sends a reset request. The transfer goes through the `NXSUSBHostShim` C target's libusb call rather than `IOHIDDeviceSetReport`/`GetReport` or Apple's IOUSBHost framework: on this composite descriptor (Audio + HID + vendor reset), the HID report path truncates the reply, and IOUSBHost's `IOUSBHostInterface`/`IOUSBHostDevice` both require exclusive access that collides with the system's own HID and Audio drivers already attached to the device's other interfaces, while libusb's control-transfer path claims nothing. Report exchange runs off the main thread; reconnecting after a disconnect never resends a stale reply.

Both discovery and transport are protocols so tests inject fakes for disconnect/reconnect, stale or malformed replies, and identity mismatches without a physical board.

The Library panel's RENAME key opens a rename form that writes a new name to the board via the `SET_NAME` wire operation; the firmware stores it in a fixed 32-byte flash field alongside the DSP snapshot (`Firmware/Core/storage.c`). `BoardMonitor.setDeviceName(_:)` re-queries capabilities after a successful write so the Library panel and the status column show the new name at once, but the name is read by macOS only at USB enumeration, so the renamed board keeps its old name until it resets or is replugged.

`Firmware/USB/descriptors.c`'s `tud_descriptor_string_cb` serves the name under two separate USB string indices, both falling back to their own fixed literal when unset: index 2 is the device's `iProduct` string, read by `system_profiler SPUSBDataType` and `ioreg`'s `kUSBProductString`, and index 4 is the Audio Control interface's own `iInterface` string (set via `TUD_AUDIO_DESC_STD_AC`'s third argument in the configuration descriptor), which is what macOS Sound settings, Audio MIDI Setup, and `system_profiler SPAudioDataType` actually name the device from. Updating only index 2 left Sound settings showing the fixed literal after a rename (issue 27); both indices must track `product_name` together.

Unlike the capabilities request, `SET_NAME` replies only after its flash write completes, which outlasts its own USB transaction; a one-shot transfer observed against the bench specimen returned whatever reply the device had buffered from the previous exchange and failed to validate. `USBHostBoardTransport.exchangeUntilComplete` resends the identical request and polls its reply up to an overall ten-second budget instead, which the device accepts as the same request already in flight rather than a new one.

Every profile edit mirrors to a verified board automatically, debounced the same 250 ms as the local save (`WorkbenchModel.scheduleBoardApply()`, `BoardMonitor.apply(_:)`, the `APPLY_STATE` wire operation), exactly as edited. There is no manual send action: an editor that requires a separate push before a change is audible does not behave like a live monitor, which is what this screen is for. The push is silently skipped whenever no board is `.verified`, and it never writes to flash, so a reconnect or power cycle reverts to the board's last persisted generation. On-device verification on 2026-10-20 confirmed the full path end to end: an applied snapshot reads back from `READ_STATE` with the exact edited values, and the specimen was audible. The specimen's speaker safety margins (excursion, thermal) are still not established (see [issue 3](https://github.com/phranck/NeXTsound/issues/3)); the owner accepted that risk explicitly after confirming the path worked, rather than the app clamping it. The same first on-device test also showed that macOS does not reliably isolate per-device output volume: driving an unusually quiet device (the SoundBox, attenuated by this DSP stage on top of its own volume) to a loud system volume and then switching the default output can carry that volume to a normally-calibrated device. That is a system behavior outside this app's control; the mitigation is keeping the SoundBox's own attenuation in an audible range instead of relying on system volume to compensate.

`WorkbenchModel` keeps at most one board write in flight, whether an apply or a save; an edit that arrives while one is already running only marks a follow-up as pending instead of starting a second, independent call, since every board exchange is serialized on `USBHostBoardTransport`'s own dispatch queue and a second call would otherwise queue up behind the first with its own timeout clock already ticking. `USBHostBoardTransport` itself keeps one libusb context and device handle open for the whole connection rather than reopening around every exchange, both because repeated `libusb_init`/`libusb_open`/`libusb_close`/`libusb_exit` cycling is the pattern libusb's own documentation discourages and because it is a known source of fragile control-transfer behavior against Apple's own USB Audio kernel extension on a composite device that also exposes an Audio Class interface. A System Settings volume control that stops responding to the connected SoundBox until it is physically replugged was observed before this change and is suspected, not yet confirmed, to be addressed by it.

### Saving to the SoundBox

The front panel's SAVE button saves the current profile on the board, so the board starts with it after the next power-up (`WorkbenchModel.saveToBoard()`, `BoardMonitor.persist()`, the `PERSIST_STATE` wire operation). The save applies the profile first, so the board stores exactly what it plays. It then writes that to flash and waits for the flash write the same way a rename does. A save requested while an apply runs follows that apply through the same single board write.

The status column's flash line says whether the board starts with the settings it plays (`BoardMonitor.storage`). Every reply carries the board's active generation, which advances with each applied snapshot, and the status reply carries the generation the board persisted. The two agree exactly when the board plays its saved settings. The monitor reads them after verifying a board, after a rename and after a save, and about once a second for as long as the board stays verified, and it marks the board unsaved after an apply. That periodic read waits while a write is on the wire and drops a reply that a write overtook, so it never contradicts the mark. It also brings the board's live values: streaming, host volume and mute, the processing load and the underrun and overrun counts. A rename also saves the settings the board plays, because the firmware stores them together with the name. A board without usable storage shows that on the flash line, and SAVE does nothing for it. A failed save shows its reason on the display's message line, as other board errors do, and leaves the flash line on not saved.

The message line shows a save while it runs and its outcome after it, then board and profile errors, the profile's validation problem and the library's storage status, in that order of precedence. SAVE's LED lights when it is pressed and drains away shortly after. The FLASH button opens the flash sheet described below.

## Firmware flashing

The front panel's FLASH button opens a sheet with a single "Flash" action: no file picker, because the app always ships the exact firmware it was built alongside. It writes that bundled `.uf2` image onto the connected board and verifies it by readback, through `FlashService`, which wraps the embedded `picotool` binary rather than talking BOOTSEL USB itself. When a board is currently connected and verified, `FlashService` passes its known serial straight to `picotool load -v -F`, which force-reboots that exact board into BOOTSEL (tracked internally by serial, since the ROM bootloader's VID/PID can be white-labelled on RP2350) and leaves it in BOOTSEL regardless of outcome; without a connected board, the sheet asks the owner to hold the board into BOOTSEL by hand and `FlashService` polls `picotool info -d` by the fixed BOOTSEL VID/PID (`0x2e8a:0x000f`, see [Backup.md](Backup.md)) until it enumerates. Either way, the actual `picotool load -v` only runs once the board is confirmed in BOOTSEL, and `FlashService` only issues the final `picotool reboot` back into the application when that load and verify succeeded; a failed write leaves the board in BOOTSEL rather than booting a bad image.

Both the firmware image and the tool that writes it are generated, gitignored `Package.swift` resources, bundled into the app the same way any other Swift package resource is; the app never depends on a user locating a `.uf2` file or a system picotool install. `Scripts/bootstrap-picotool-usb.sh` builds `picotool` from the exact commit `toolchain.json` already pins (`firmware.picotool.commit`), directly against Homebrew's `libusb`, the same dependency `NXSUSBHostShim` links; the project-local `.tools/picotool` (built by the Pico SDK's own glue with `-DPICOTOOL_NO_LIBUSB=1`) stays USB-incapable and is used only for `picotool info -a` on a built UF2. `Scripts/firmware.sh` copies its own build output, `nxs_firmware.uf2`, into the same Workbench resources directory as its last step, so building the firmware always refreshes what the app embeds. `Scripts/app.sh` now builds the firmware before the app for exactly this reason, and both it and `Scripts/check.sh` run the picotool bootstrap script first; building the macOS app therefore requires the full firmware toolchain (the ARM cross compiler and Pico SDK), a deliberate trade against a quicker app-only build.

While a phase runs, the sheet shows its status text next to a determinate `ProgressView`; `FlashPhase.progress` is a fixed position per phase (picotool reports no byte-level progress for `load -v`), not a measured completion fraction. "Firmware written and verified." only means the write and readback-verify succeeded, not that the board is confirmed back online: picotool only ever talks to a device in BOOTSEL mode, so it cannot see the application firmware it just rebooted into. Once flashing succeeds, the sheet additionally shows the live `BoardConnectionState` from the same `BoardMonitor`/HID discovery that drives the front panel's status column, so the owner sees the actual reconnect (or its absence) rather than an assumption drawn from a successful `picotool reboot` call.

This has not been exercised against real hardware; see [issue 41](https://github.com/phranck/NeXTsound/issues/41).

## Fixed enclosure data

[`Enclosure-2026-10-21.json`](Verification/Enclosure-2026-10-21.json) is the current net internal air volume (Vb) record; it supersedes and replaces `Enclosure-2026-10-18.json` in full, which described an earlier, not yet acoustically sealed design. The owner modeled the interior air cavity as its own solid in Shapr3D (the current, final enclosure design), exported it, the driver, and the RP2350 board separately, and each part's volume was computed via the divergence theorem over its mesh's connected components. The source STL files stay private outside Git.

`NeXTsoundCore.EnclosureRecord.nextSoundBoxMini()` carries the resulting figures (internal cavity, driver and board displacement, net Vb) for code to consume, with `modelReference` pointing at the verification file above. `NeXTsoundCore.ClosedBoxAlignment` uses this Vb together with a driver's Fs/Qts/Vas to compute the sealed box's own Fc/Qtc acoustic response; see [DSP.md](DSP.md#closed-box-alignment). Neither panel offers an enclosure, because the product has exactly one fixed enclosure rather than a choice to present.

## Reproducible configuration

- `toolchain.json` owns the Xcode and generator pins.
- `App/Workbench/Package.swift` owns the native deployment minimum.
- `ProfileFile` owns the exported profile's type identifier and file extension.
- `WorkbenchLayout` owns the windows' identifiers and titles.
- `FrontPanelDisplayLayout` owns the display's plotted gain range.

`Scripts/app.sh` derives generator environment values from these sources. `NeXTsoundWorkbenchRender --document-type` emits the exported profile's type JSON without creating a window or initializing the rendering application. The generated Xcode project and property lists stay ignored. The generator runs from its packaged executable so its bundled setting presets remain available.

The `NXSUSBHostShim` target links Homebrew's `libusb` (`brew install libusb`) from `/opt/homebrew`, unlike the checksum-pinned tools above; it is not version-pinned. Homebrew on Apple Silicon only ships an arm64 build, so the app targets `ARCHS: arm64` in `App/project.yml` rather than the default universal set.

```bash
xcrun swift run --package-path App/Workbench NeXTsoundDiagnostics
```

Polls `NXS_OPERATION_STATUS` every 200 ms through the same `USBHostBoardTransport` the app uses, printing `isStreaming`/`inputPeak`/`outputPeak`/underrun and overrun counts/`maxProcessingUs`/mute state. Lets the owner watch the firmware's own view of the USB audio stream live, independent of CoreAudio and of this app's UI, for diagnosing whether audio data is reaching the board at all.

## Tests and rendering

```bash
xcrun swift test --package-path App/Workbench
xcrun swift run --package-path App/Workbench NeXTsoundWorkbenchRender "$PWD/.build/app-render"
```

The renderer runs with activation prohibited and opens no window. It renders the front panel without and with a board, and the Library panel, at scale 2 through SwiftUI's own renderer, which draws a placeholder over the area of any AppKit view. The panels' AppKit views therefore take no room. These images show the implemented SwiftUI content, not screenshots of a running NeXTsound application.

Tests cover canonical round trips, malformed input, directory rejection, revision/identity failures, atomic edits, metadata preservation, analytical response, display geometry, library validation/limits, store load/save/corruption recovery, board disconnect/reconnect, stale and malformed replies, identity mismatch, device name round trips (including the shared space-permitting validation and the firmware's fixed-length flash storage), a broken store never blocking the model from becoming ready, the driver library's validation, persistence round trips, and its independence from any connected board, the debounced auto-apply action sending the edited profile's settings unchanged to a verified board while silently skipping without one, with error surfacing on a genuine transport failure, saving to the board applying the profile before persisting it, a failed save leaving the board unsaved, a board without storage never receiving a save, a save requested during an apply following it, the storage state read from the active and persisted generations, and the A/B slots: capture leaving the library untouched and isolated from later edits, recall changing only the DSP settings with undo support, and recall of an empty slot being a no-op. The directory case was observed crashing before checking `isRegularFile` ahead of `regularFileContents`. `FlashServiceTests` exercises the picotool command sequence and phase order against a fake runner for both the known-serial and unknown-serial paths, that a failed write never issues the final reboot, and that a board never appearing in BOOTSEL times out; none of this has run against the embedded picotool binary talking to real hardware. The Library panel's tests cover selection, renaming, the profile keys and the speaker choice going through the model's edit path, the lines of its list and readouts, captions that break only between words, and every dot of both panels falling on whole device pixels at scale 2. A window test hosts the front panel under a hidden title bar and checks that the window takes the panel's size and shows the metal in every pixel of its top and bottom rows. A layout test checks that the row of modules gives a one-slider module two thirds of the limiter's width, and another that an indicator's caption starts level with the top of the key beside it while the row stays as tall as the key.

Localization has no dedicated test suite; it is verified by the build producing a `de.lproj` bundle for the app target and for each Swift package's resource bundle, and by every string catalog key holding a German translation.
