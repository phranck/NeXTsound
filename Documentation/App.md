# Native workbench

NeXTsound is a SwiftUI app for macOS 26 and later. Its main window is the front panel, which shows the Library panel as a sheet, and it manages a local profile library. It discovers compatible SoundBoxes and shows their connection status, custom name, and firmware version through a read-only capabilities query, can write a new persisted name to the board, mirrors every profile edit to the board automatically for live listening, saves the current profile on the board when asked to, and shows a live spectrum of what the SoundBox plays. A mirrored edit lives only in the board's memory, so a reconnect or power cycle reverts to the board's last saved DSP state. No write resets the board or changes the system audio output. Generation-aware negotiation and retries remain tracked in [issue 16](https://github.com/phranck/NeXTsound/issues/16).

## Build

From the repository root:

```bash
bash Scripts/app.sh
```

The command selects the Xcode version from `toolchain.json`, bootstraps the checksum-pinned XcodeGen, generates `App/NeXTsound.xcodeproj`, and builds Debug and Release, both signed ad hoc (see [Firmware flashing](#firmware-flashing)). It does not launch or install the app.

Build products:

- `.build/macOS/Build/Products/Debug/NeXTsound.app`
- `.build/macOS/Build/Products/Release/NeXTsound.app`

The complete repository gate is `bash Scripts/check.sh`. It includes shared and app package tests, formatting/lint, Release packages, all RP2350 targets and guards, and both native app configurations.

### Version and build number

Nobody edits the app's version or build number. `Scripts/app-version.sh` derives both from git, and `Scripts/app.sh` hands them to XcodeGen, which writes them into the Info.plist. The About window shows them.

- The build number is the number of commits reachable from `HEAD`, so it grows along `main`.
- The version is the one in the app tag on `HEAD`, written `app-v<major>.<minor>.<patch>`. Without such a tag on `HEAD`, it is the next version after the latest app tag: a `Feat:` commit since that tag raises the minor version, and otherwise a `Fix:` commit raises the patch version. Without any app tag, it counts from 0.1.0.
- The firmware keeps its own version in `Firmware/CMakeLists.txt`.

`Scripts/test-app-version.sh`, part of the gate, checks each rule against throwaway repositories.

A new version is a tag on `main` and a GitHub release:

```bash
version=$(bash Scripts/app-version.sh | cut -d ' ' -f 1)
git tag "app-v$version" && git push origin "app-v$version"
bash Scripts/app.sh
ditto -c -k --keepParent .build/macOS/Build/Products/Release/NeXTsound.app "NeXTsound-$version.zip"
gh release create "app-v$version" --draft --title "NeXTsound $version" --notes-file <notes> "NeXTsound-$version.zip"
```

The release stays a draft until its asset has been downloaded, unpacked, and reports the tag's version, and only then is it published.

## Source layout

The app target compiles `App/Application/NeXTsoundApp.swift` alone, and every other part of the app lives in the Swift package `App/Workbench`. The folders of its `NeXTsoundWorkbench` target name the kind of code they hold: `Models`, `Persistence`, `Services`, `Presentation` for the types that turn state into what a view shows, `Views` with one folder per window or sheet, `Controls`, `DotMatrix`, `Layout`, `Modifiers`, `Extensions`, `Commands` and `Theme`. A file holds one kind of code, and a helper that only one file uses stays in that file. The tests use the same folders, and their fakes and pixel reader sit in `Support`.

Views lay out and draw. What a readout shows, whether a key is enabled and what a key does to the model are decided in a model or a presentation type, so a unit test reaches each decision without rendering a view. The display color reaches the dot matrix through the environment, which the front panel and the Library panel set from the stored choice.

## App icon

`App/Application/AppIcon.icon` is the app's icon, an Icon Composer file that Xcode compiles for every size and appearance. XcodeGen adds it to the app's resources with the rest of `App/Application`, and the target's App Icon setting names it.

From the back to the front, it shows the display's dot grid on dark glass, the blue phosphor EQ curve with a dim area under it, the four LAYERED stripes along the bottom, and a speaker driver rendered in Blender, which reaches into the red stripe and casts its shadow on the stripes. The grid starts two rows below the top edge, because the glass rim that macOS draws around every icon smears whatever lies there. The driver brings its own light and shadow, so the system adds neither to it.

A sound profile file has an icon of its own, `App/Icons/ProfileIcon.icon`. It shares every layer with the app icon except the driver, whose place a sheet of paper with a folded corner takes, rendered with the same camera, lights and shadow. Printed on the sheet in Inter Tight SemiBold Italic is Steve Jobs' quote that begins "Sometimes life hits you in the head with a brick", justified and flowing around the folded corner, signed in Inter Tight Bold behind an em dash. The script finds the largest size at which the quote fills the sheet down to a centered line near the bottom edge, "-- printed on a NeXT Laser Printer, 400 dpi --", in SemiBold. The file lies outside `App/Application`, so Xcode does not take it for the app icon. `Scripts/app.sh` runs `Scripts/profile-icon.sh`, which renders it with Icon Composer's `ictool` at every size an `.icns` holds and writes `App/Generated/ProfileIcon.icns`. The app bundles that file, and the profile type names it in `UTTypeIconFile`. The `ictool` that `xcrun` finds is a different tool without `--export-image`, so the script takes the one inside Icon Composer.

To change the icons, edit their scripts and run:

```bash
bash Scripts/app-icon.sh
```

`Scripts/app-icon-render.py` renders a subject in Blender's Cycles, the driver or the sheet, and `Scripts/app-icon-layers.py` writes the vector layers and `icon.json` around it. The script needs Blender, fontTools and the network. Its first argument sets the samples, 256 by default, and further arguments name the subjects to render, `driver` and `sheet` by default. Icon Composer opens the result, and its `ictool` renders a preview:

## Front panel

The front panel is the app's main window (`Window(id: WorkbenchWindows.frontPanelWindowID)`), and closing it quits the app, even while the About or the Driver Models window is open. Its metal reaches under the hidden title bar, and the window takes the size of the panel. The metal, which the Library sheet shares, shows a grain of light and dark specks. The NeXTSOUND wordmark and the header's four LAYERED stripes are pressed into the metal, each letter and each stripe on its own. The letters are a shaded recess, and the stripes keep their colors. Both are darker along their upper edges, and their lower edges catch the light. A drag anywhere on the panel moves the window, unless it starts on a control.

The multifunction display under the header plots the selected profile's response from the five EQ bands and, while it is enabled, the high-pass. The plot uses the shared DSP coefficients. It leaves out attenuation, mute and the limiter, so it is not an acoustic measurement, and it clips the curve at ±15 dB without changing the settings. The curve stands between a gain scale at its left, labeled every 5 dB from -10 to +10 dB, and a frequency scale under it, labeled at 20 Hz, 100 Hz, 1 kHz and 10 kHz. An axis runs along its left and its bottom edge, and dotted lines mark the labeled values. The axes, the grid and the labels are a step dimmer than the status column's labels, so the curve stands out. The area under the curve fills down to the bottom axis in the curve's color, strongest at the graph's top and fading out toward the axis, and the grid lines stay visible over it. Each enabled EQ band shows a round dot on the curve at its frequency, set off from the curve, the fill and the grid by an unlit edge. The band the band keys select lights a step brighter than the curve, and the others in the grid's dimmer step. A disabled band shows no dot. The profile's name stands under the frequency scale. The status column at the right shows the SoundBox's connection, and for a verified board its name, serial, firmware, audio format, flash size with the storage state, and live values. A board with owner details adds a line for each one that is set: the owner, the unit number, the date, and the note's first line. The column slides out to the right and back in, in whole dot columns over the unlit dots, and while it is out the curve and the profile's name take the whole display. With Reduce Motion, it appears and disappears without sliding. Messages show in a card with rounded corners over the middle of the display, whether the column is in or out. The card's frame is a step dimmer than its text, a ring of unlit dots that follows its rounded corners sets it apart from what lies beneath it, and a message takes at most four lines of 48 characters. While the card shows, everything else on the display lights dimmer. An error shows at once and stays while it is current. Any other message shows once it has been current for half a second, so a state that passes in a moment never flashes up, and it leaves after four seconds. A save to the SoundBox stays while it runs. The message shown last does not show again until another one has.

While the SPECTRUM key is down, the [live spectrum](#live-spectrum) takes the curve's place. Its bars stand over the same frequency scale, one bar for each sixth of an octave with an unlit dot column between neighbors. The scale at its left shows the level below full scale, labeled every 10 dB from -10 to -50 dB, with full scale on the top row and -60 dB on the bottom axis. Each bar's top row lights in the curve's color and the rows under it in the curve's fill. The band markers do not show, and the profile's name stays under the frequency scale.

The row of controls under the display edits the selected profile. The band panel's three sliders set the band that its five keys select, and the Edit menu and each band key's context menu enable or reset a band. The high-pass, output and sample-peak limiter modules hold the other sliders, the toggles for the high-pass and for mute, and the SAVE and FLASH buttons described below. Master Volume reaches +12 dB, where the level rises above full volume and the limiter holds every peak at its ceiling. Its slider follows a mixing console's fader law: 0 dB sits at three quarters of the travel, the range from -12 to +12 dB takes almost half of it, and the steps grow toward -80 dB, so an arrow key moves it by about half a decibel near 0 dB. The slider stops at the end of the range the verified board reports, which is 0 dB for firmware before 0.4.0, and every write to the board keeps the profile within that range. A new profile starts at 0 dB, muted. The keys at the right end choose the displays' color, which the app keeps across launches. Directly under BLUE, the SPECTRUM key switches the display between the EQ curve and the live spectrum, and directly under AMBER, the INFO key slides the display's status column in and out. Each key stays down with its LED lit while its view shows. The app keeps both states across launches, and the View menu's Show Spectrum, Hide Spectrum, Show Info and Hide Info do the same as the keys. At the bottom, the LIBRARY key shows the Library panel as a sheet and stays down with its LED lit until the sheet closes. The radio keys, which are the band keys and the display color keys, keep the kit's gray. Every push key, which starts an action or latches, has the yellow of the header's stripes, on the front panel and in the Library alike, and the round FLASH button has their red. A slider follows the arrow keys, Page Up, Page Down, Home and End, and the frequency, quality and release sliders give every decade the same travel. The ticks beside a slider stand on round values of its parameter, where its scale puts them: the 1, 2 and 5 of every decade on the frequency, quality and release sliders, every 3 dB on the band gain and the limiter's ceiling, and -80, -60, -40, -30, -20, -10, 0, +6 and +12 dB on Master Volume. The 0 dB tick of the band gain and of Master Volume is longer than the others, and a slider shows no tick beyond the range the verified board reports. Every edit registers its undo, is saved, and plays on a connected SoundBox.

## Live spectrum

The spectrum shows what the verified SoundBox sends to its amplifier. The app taps the audio macOS sends to the board and runs it through the board's processing in the firmware's order (`SpectrumSignal`): the host volume the board reports, the firmware's own DSP engine with the selected profile's settings (`DSPEngine`, see [DSP.md](DSP.md#engine-on-the-mac)), and the host's mute. An edit reaches the spectrum as it reaches the board, after the same crossfade. The spectrum is the board's computation repeated on the Mac, not a measurement at the amplifier, and the speaker's response in the box is not part of it. The firmware has no part in it, because the processing high-water mark of its audio owner already reaches the block deadline ([Diagnostics-2026-10-24.json](Verification/Diagnostics-2026-10-24.json)).

`SpectrumMonitor` measures only while the SPECTRUM key is down and a board is verified. It finds the board's Core Audio output by its USB serial and its vendor and product ID (`SoundBoxAudio`), and `CoreAudioSpectrumSource` taps that output with a private Core Audio tap that leaves the audio playing. A private aggregate device holds the tap, as Apple's [Capturing system audio with Core Audio taps](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps) describes. Releasing the key or losing the board destroys both. The first measurement asks for permission to record system audio, and the Info.plist's `NSAudioCaptureUsageDescription` explains why. A measurement that cannot start shows its reason in the display's message card and tries again every second while the key stays down and the board stays verified. A board that reconnects verifies over USB before Core Audio lets the app record its output, so the spectrum comes back on its own a moment later.

`SpectrumAnalyzer` takes the DSP's mono output and transforms its last 8192 samples with a Hann window, 30 times per second of audio. It sums each band's power, so a full-scale sine reads 0 dB on the band that holds it. The 59 bands are sixths of an octave around 1 kHz, from 21 Hz to 19 kHz, and they stay the same whatever width the graph has. At 48 kHz the transform's bins lie 5.9 Hz apart, which is wider than the lowest bands, so a low tone also lights the bands next to it. A band rises at once and falls at 40 dB per second.

## Profile library

`ProfileLibrary` is the internally managed collection of profiles; `ProfileLibraryStore` persists it as validated atomic local JSON under Application Support, independent of any file the user opens or saves. `ProfileFile` wraps the existing `SoundProfile` for exactly one purpose: it is the `FileDocument` adapter behind SwiftUI's `fileImporter`/`fileExporter`, so a profile's canonical validated JSON can be imported or exported explicitly. Profile files end in `.nxsbprofile`, and JSON profiles can also be imported. An exported file has its extension hidden, so the Finder shows the profile's name alone unless its "Show all filename extensions" setting is on. `fileExporter` has no option for this, so the exporter sets the file's `hasHiddenExtension` once it is written. A profile file holds JSON, but its type conforms to `public.data` rather than `public.json`: the Finder's icon view shows a Quick Look thumbnail wherever Quick Look can render the content, and for a JSON type that is a text preview in place of the profile icon. The declaration in `App/project.yml` is the one that counts. Launch Services answers for the type with the installed app's declaration, so a unit test cannot check the one in `UTType.neXTsoundProfile`. The app owns the exported profile type and registers as its editor in `CFBundleDocumentTypes`, so the Finder opens a profile file in the app. Generic JSON is not registered. The front panel receives the file through `onOpenURL` and declares with `handlesExternalEvents(preferring:allowing:)` that it takes every external event. Without that declaration SwiftUI opens a new instance of the front panel's `Window` scene for the file, which closes the open window and with it the app. `WorkbenchModel.openProfile(at:)` waits for the stored library to load, because a file that launches the app arrives first and the load replaces the library. It then imports the profile and selects it, as the IMPORT key does.

`WorkbenchModel` is the single `@Observable` source of truth: it owns the library, mediates every mutation through validation, registers native undo via the window's `UndoManager`, and debounces persistence. A failed load never blocks editing or quitting; it shows in the display's message card while edits continue in memory until storage recovers.

Two volatile A/B slots hold a captured `DSPSettings` snapshot each, for comparing variations during a single editing session. Capture copies the current profile's DSP settings into a slot; recall replaces only the current profile's DSP settings with a slot's capture, through the same validated edit transaction as any other change, so it advances the revision and supports undo. Neither slot is serialized, included in the saved library, or sent to a connected SoundBox on its own; they exist only in memory and are lost when the app quits. This is model-layer only for now; neither panel has A/B controls.

## Driver library

`DriverRecord` is a driver model entry the owner maintains by hand: Thiele/Small, electrical, mechanical, thermal, and dimensional parameters, a name/manufacturer, and an optional source. Missing parameters stay `nil` rather than defaulted. `DriverLibrary` is the validated collection, seeded by default with `DriverLibrary.knownCandidates`: the driver currently in use (Tectonic Elements TEBM28C10-4) plus researched candidates within the enclosure's size and depth envelope (Tectonic TEBM28C10-4B and -4BE, Dayton Audio CE41N-4, Visaton FR 58 in 4Ω and 8Ω, Visaton BF 37 in 4Ω and 8Ω). Each candidate's fields come only from its own manufacturer datasheet; a field stays `nil` where that datasheet does not give it directly, rather than computed from related fields or taken from a third-party aggregation that cannot be checked against the manufacturer's own source. `DriverLibraryStore` persists the library as atomic local JSON under Application Support, the same pattern `ProfileLibraryStore` uses (both now share the bounded atomic read/write in `AtomicJSONFile`). Like the profile store, it refuses to save until a load has succeeded, so an unreadable or oversized file stays on disk instead of being replaced by the default library; edits made meanwhile stay in memory and the window shows the save error. `DriverLibraryModel.start()` merges any known candidate not yet present (by id) into an already-persisted library, so a library saved before a new candidate was researched picks it up on the next launch. `DriverLibraryModel` is the `@Observable` CRUD state behind the Library panel's DRIVER MODELS key, which opens it in its own window (`Window(id: WorkbenchWindows.driverLibraryWindowID)`) rather than a sheet, so it stays open alongside the main window; it holds no reference to `BoardMonitor` or any board transport, so adding, editing, or removing a driver model never writes to a connected board. A selected entry's parameters are copied into a profile's `SpeakerRecord` snapshot rather than referenced live, matching the existing catalog/snapshot separation; the DSP calculation that reads a selected entry is [issue 19](https://github.com/phranck/NeXTsound/issues/19)'s own work.

An accepted edit advances the profile revision atomically. Failed edits and exhausted revisions leave the library unchanged. An incomplete name can remain in the library but fails validation on export. A new profile always starts flat and digitally muted (`FactoryPreset.flat`, the same settings a default `DSPSettings()` already produces); there is no starting preset to choose, since the owner builds every real profile by hand. `FactoryPreset`'s other cases (`warm`, `speech`) remain fixture data for the offscreen renderer and for tests, not a feature exposed in the app. The driver form's focus is its Thiele/Small, electrical, mechanical, and mounting parameters; a candidate researched from a manufacturer datasheet shows that datasheet as a clickable "Datasheet" link (its first `sourceURL`) rather than a bundled image or 3D model.

## Library panel

The Library panel is a sheet on the main window, which the front panel's LIBRARY key and the View menu's Show Library open. Its Profiles, Speaker and SoundBox sections stand side by side, each as wide as the four profile keys. The CLOSE key at its bottom right closes it and releases the LIBRARY key. Escape does not close the sheet, because a key bound to Escape would take Escape before a rename does. While the sheet is shown, the import and export panels open over it. Its sections follow the front panel's style, and its readouts take the display color that the front panel's keys choose.

The Profiles section lists the library's profiles on seven lines and marks the selected one. A click or the arrow keys select a profile. A double click or Return renames it in place, with a blinking cursor at the caret, and the typing goes to an invisible AppKit text field whose delegate sees Return and Escape before the panel does. Return or a click elsewhere keeps the new name, and Escape keeps the old one. The NEW, DELETE, IMPORT and EXPORT keys add, delete, import and export a profile, and the File menu offers the same as New Profile (⌘N), Delete Profile, Import Profile… (⌘O) and Export Profile… (⇧⌘E). A profile file double-clicked in the Finder opens the app, joins the library and is selected, so it plays on a connected SoundBox at once. The last profile cannot be deleted.

The Speaker section shows the selected profile's speaker on two lines. A click, Space, Return or the down arrow opens the native menu of every driver model over the readout. The DRIVER MODELS key under it opens the Driver Models window.

The SoundBox section shows the verified board's name on two lines, broken between its words as the speaker's name is, or No SoundBox and Not verified otherwise. The CONNECTED LED stands at the right end of the section's title, on its baseline, with its caption to its left. It is lit while a board is verified, and only then does the key under the readout open the board's form. A board whose owner details the app read gets the EDIT key and the form for its name and owner details, described under [owner details](#owner-details-and-serial-numbers). Any other board gets the RENAME key and the rename form.

## Localization

The app is localized into English (development language) and German. Three String Catalogs carry the translations: `App/Application/InfoPlist.xcstrings` for the bundle name and the exported document type's description, `NeXTsoundWorkbench`'s own `Resources/Localizable.xcstrings` for every UI string of the app's windows, and `NeXTsoundCore`'s own `Resources/Localizable.xcstrings` for the shared model's validation and factory-preset strings. Each Swift package declares `defaultLocalization: "en"` and ships its catalog as a processed resource, so `Text`/`Button`/`.help(...)` literals resolve through the package's own resource bundle rather than the app's.

A `LocalizedError.errorDescription` or any other computed `String` built from a literal is not picked up by Xcode's source scanner on its own; each one is wrapped in `String(localized:)` so it participates in the catalog. `WireError`'s message is the one deliberate exception: it comes from the shared C protocol library's `nxs_result_description`, a wire-protocol debug string compiled into firmware and host alike, and stays English-only rather than duplicating a translation table across the Swift/C boundary.

Each button in the Driver Models window's toolbar has a `.help(...)` tooltip, translated alongside its label.

## Board discovery

`BoardMonitor` tracks one `BoardConnectionState`: disconnected, detected (matched by USB identity, not yet verified), verified (with the firmware's reported `DeviceCapabilities`), or mismatched (an invalid reply or a reported serial that disagrees with the enumerated device). `IOHIDBoardDiscovery` finds compatible boards through `IOHIDManager`, matching the canonical vendor/product ID and HID usage from `BoardIdentity`, without seizing the device. `USBHostBoardTransport` exchanges feature reports as raw USB class control transfers and validates each reply's identity, operation, and size before decoding it. It sends the capabilities and status requests, which change nothing, and the apply, rename, and save writes described below; it never sends a reset request. The transfer goes through the `NXSUSBHostShim` C target's libusb call rather than `IOHIDDeviceSetReport`/`GetReport` or Apple's IOUSBHost framework: on this composite descriptor (Audio + HID + vendor reset), the HID report path truncates the reply, and IOUSBHost's `IOUSBHostInterface`/`IOUSBHostDevice` both require exclusive access that collides with the system's own HID and Audio drivers already attached to the device's other interfaces, while libusb's control-transfer path claims nothing. Report exchange runs off the main thread; reconnecting after a disconnect never resends a stale reply. An exchange that the board does not answer ends for its caller after two seconds through `withTimeout`, while the blocked libusb call finishes on its own queue and its late reply is dropped. A task group could not bound it, because a group waits for every child and the blocked call ignores cancellation.

Both discovery and transport are protocols so tests inject fakes for disconnect/reconnect, stale or malformed replies, and identity mismatches without a physical board.

The Library panel's RENAME key opens a rename form that writes a new name to the board via the `SET_NAME` wire operation; the firmware stores it in a fixed 32-byte flash field alongside the DSP snapshot (`Firmware/Core/storage.c`). `BoardMonitor.setDeviceName(_:)` re-queries capabilities after a successful write so the Library panel and the status column show the new name at once, but the name is read by macOS only at USB enumeration, so the renamed board keeps its old name until it resets or is replugged.

`Firmware/USB/descriptors.c`'s `tud_descriptor_string_cb` serves the name under two separate USB string indices, both falling back to their own fixed literal when unset: index 2 is the device's `iProduct` string, read by `system_profiler SPUSBDataType` and `ioreg`'s `kUSBProductString`, and index 4 is the Audio Control interface's own `iInterface` string (set via `TUD_AUDIO_DESC_STD_AC`'s third argument in the configuration descriptor), which is what macOS Sound settings, Audio MIDI Setup, and `system_profiler SPAudioDataType` actually name the device from. Updating only index 2 left Sound settings showing the fixed literal after a rename (issue 27); both indices must track `product_name` together.

Unlike the capabilities request, `SET_NAME` replies only after its flash write completes, which outlasts its own USB transaction; a one-shot transfer observed against the bench specimen returned whatever reply the device had buffered from the previous exchange and failed to validate. `USBHostBoardTransport.exchangeUntilComplete` resends the identical request and polls its reply up to an overall ten-second budget instead, which the device accepts as the same request already in flight rather than a new one.

Every profile edit mirrors to a verified board automatically, debounced the same 250 ms as the local save (`WorkbenchModel.scheduleBoardApply()`, `BoardMonitor.apply(_:)`, the `APPLY_STATE` wire operation), exactly as edited. There is no manual send action: an editor that requires a separate push before a change is audible does not behave like a live monitor, which is what this screen is for. The push is silently skipped whenever no board is `.verified`, and it never writes to flash, so a reconnect or power cycle reverts to the board's last persisted generation. On-device verification on 2026-10-20 confirmed the full path end to end: an applied snapshot reads back from `READ_STATE` with the exact edited values, and the specimen was audible. The specimen's speaker safety margins (excursion, thermal) are still not established (see [issue 3](https://github.com/phranck/NeXTsound/issues/3)); the owner accepted that risk explicitly after confirming the path worked, rather than the app clamping it. The same first on-device test also showed that macOS does not reliably isolate per-device output volume: driving an unusually quiet device (the SoundBox, attenuated by this DSP stage on top of its own volume) to a loud system volume and then switching the default output can carry that volume to a normally-calibrated device. That is a system behavior outside this app's control; the mitigation is keeping the SoundBox's own attenuation in an audible range instead of relying on system volume to compensate.

`WorkbenchModel` keeps at most one board write in flight, whether an apply or a save; an edit that arrives while one is already running only marks a follow-up as pending instead of starting a second, independent call, since every board exchange is serialized on `USBHostBoardTransport`'s own dispatch queue and a second call would otherwise queue up behind the first with its own timeout clock already ticking. `USBHostBoardTransport` itself keeps one libusb context and device handle open for the whole connection rather than reopening around every exchange, both because repeated `libusb_init`/`libusb_open`/`libusb_close`/`libusb_exit` cycling is the pattern libusb's own documentation discourages and because it is a known source of fragile control-transfer behavior against Apple's own USB Audio kernel extension on a composite device that also exposes an Audio Class interface. A System Settings volume control that stops responding to the connected SoundBox until it is physically replugged was observed before this change and is suspected, not yet confirmed, to be addressed by it.

### Owner details and serial numbers

A board whose capabilities report the metadata feature carries owner details: a date the owner chooses, a serial number, the owner's name and a note ([Protocol.md](Protocol.md#owner-metadata)). `BoardMonitor` reads them when the board verifies and after every write. The Library panel's EDIT form edits the name and the four details together. The serial number reads as the prefix NXSB and at least four digits, such as NXSB0001, and the date has no time. Every field can be changed at any time, and Apply writes only what changed. The form checks the name, the owner and the note with the same shared codec as the firmware, so it refuses what the board would refuse, and it says why below the fields.

`SerialNumberRegister` keeps every number the app has written, under the chip serial of the board that carries it. `SerialNumberRegisterStore` saves it as atomic local JSON beside the profile library in Application Support. For a board without a number, the form proposes the lowest number from 1 that no other board carries, so a number that was freed is used again before a new one. NXSB0000 is the owner's test number: the form accepts it, never proposes it, and warns about no gap for it. It refuses a number another board carries and warns when a lower number is still free. A board that connects with a number the register does not hold for another board adds that number to the register. While the register cannot be read, the form gives no board a number, because the number could already belong to another board.

### Saving to the SoundBox

The front panel's SAVE button saves the current profile on the board, so the board starts with it after the next power-up (`WorkbenchModel.saveToBoard()`, `BoardMonitor.persist()`, the `PERSIST_STATE` wire operation). The save applies the profile first, so the board stores exactly what it plays. It then writes that to flash and waits for the flash write the same way a rename does. A save requested while an apply runs follows that apply through the same single board write.

The status column's flash line says whether the board starts with the settings it plays (`BoardMonitor.storage`). Every reply carries the board's active generation, which advances with each applied snapshot, and the status reply carries the generation the board persisted. The two agree exactly when the board plays its saved settings. The monitor reads them after verifying a board, after a rename and after a save, and about once a second for as long as the board stays verified, and it marks the board unsaved after an apply. That periodic read waits while a write is on the wire and drops a reply that a write overtook, so it never contradicts the mark. It also brings the board's live values: streaming, host volume and mute, the processing load and the underrun and overrun counts. A rename also saves the settings the board plays, because the firmware stores them together with the name. A board without usable storage shows that on the flash line, and SAVE does nothing for it. A failed save shows its reason in the display's message card, as other board errors do, and leaves the flash line on not saved.

The message card shows a save while it runs and its outcome after it, then board and profile errors, the profile's validation problem and the library's storage status, in that order of precedence. SAVE's LED lights when it is pressed and drains away shortly after. The FLASH button opens the flash sheet described below.

## Firmware flashing

The front panel's FLASH button opens a sheet with a single "Flash" action: no file picker, because the app always ships the exact firmware it was built alongside. It writes that bundled `.uf2` image onto the connected board and verifies it by readback, through `FlashService`, which wraps the embedded `picotool` binary rather than talking BOOTSEL USB itself. When a board is currently connected and verified, `FlashService` passes its known serial straight to `picotool load -v -F`, which force-reboots that exact board into BOOTSEL (tracked internally by serial, since the ROM bootloader's VID/PID can be white-labelled on RP2350) and leaves it in BOOTSEL regardless of outcome; without a connected board, the sheet asks the owner to hold the board into BOOTSEL by hand and `FlashService` polls `picotool info -d` by the fixed BOOTSEL VID/PID (`0x2e8a:0x000f`, see [Backup.md](Backup.md)) until it enumerates. Either way, the actual `picotool load -v` only runs once the board is confirmed in BOOTSEL, and `FlashService` only issues the final `picotool reboot` back into the application when that load and verify succeeded; a failed write leaves the board in BOOTSEL rather than booting a bad image.

Both the firmware image and the tool that writes it are generated, gitignored `Package.swift` resources, bundled into the app the same way any other Swift package resource is; the app never depends on a user locating a `.uf2` file or a system picotool install. The build signs the app ad hoc (`CODE_SIGN_IDENTITY: "-"` in `App/project.yml`), and the bootstrap script signs `picotool` itself, so the app's signature seals both resources. macOS does not check a running app's resources, so `ProcessPicotoolRunner` checks the app bundle with `BundleSeal.verify` before every start of `picotool` and refuses to run it from a bundle whose sealed files changed. Changing the executable instead takes a new signature, which changes the app's identity and with it its system audio capture permission. The app and `picotool` run with Hardened Runtime (`ENABLE_HARDENED_RUNTIME` and `codesign --options runtime`), so dyld ignores `DYLD_*` variables and library validation applies. The Release app carries no entitlements; `CODE_SIGN_INJECT_BASE_ENTITLEMENTS: NO` keeps the `get-task-allow` entitlement that Xcode adds for debugging out of it. `Scripts/bootstrap-picotool-usb.sh` builds `picotool` from the exact commit `toolchain.json` already pins (`firmware.picotool.commit`) and links Homebrew's static `libusb` into it, the same library `NXSUSBHostShim` links; the project-local `.tools/picotool` (built by the Pico SDK's own glue with `-DPICOTOOL_NO_LIBUSB=1`) stays USB-incapable and is used only for `picotool info -a` on a built UF2. `Scripts/firmware.sh` copies its own build output, `nxs_firmware.uf2`, into the same Workbench resources directory as its last step, so building the firmware always refreshes what the app embeds. `Scripts/app.sh` now builds the firmware before the app for exactly this reason, and both it and `Scripts/check.sh` run the picotool bootstrap script first; building the macOS app therefore requires the full firmware toolchain (the ARM cross compiler and Pico SDK), a deliberate trade against a quicker app-only build.

While a phase runs, the sheet shows its status text next to a determinate `ProgressView`; `FlashPhase.progress` is a fixed position per phase (picotool reports no byte-level progress for `load -v`), not a measured completion fraction. "Firmware written and verified." only means the write and readback-verify succeeded, not that the board is confirmed back online: picotool only ever talks to a device in BOOTSEL mode, so it cannot see the application firmware it just rebooted into. Once flashing succeeds, the sheet additionally shows the live `BoardConnectionState` from the same `BoardMonitor`/HID discovery that drives the front panel's status column, so the owner sees the actual reconnect (or its absence) rather than an assumption drawn from a successful `picotool reboot` call.

This has not been exercised against real hardware; see [issue 41](https://github.com/phranck/NeXTsound/issues/41).

## Fixed enclosure data

[`Enclosure-2026-10-21.json`](Verification/Enclosure-2026-10-21.json) is the current net internal air volume (Vb) record; it supersedes and replaces `Enclosure-2026-10-18.json` in full, which described an earlier, not yet acoustically sealed design. The owner modeled the interior air cavity as its own solid in Shapr3D (the current, final enclosure design), exported it, the driver, and the RP2350 board separately, and each part's volume was computed via the divergence theorem over its mesh's connected components. The source STL files stay private outside Git.

`NeXTsoundCore.EnclosureRecord.nextSoundBoxMini()` carries the resulting figures (internal cavity, driver and board displacement, net Vb) for code to consume, with `modelReference` pointing at the verification file above. `NeXTsoundCore.ClosedBoxAlignment` uses this Vb together with a driver's Fs/Qts/Vas to compute the sealed box's own Fc/Qtc acoustic response; see [DSP.md](DSP.md#closed-box-alignment). Neither panel offers an enclosure, because the product has exactly one fixed enclosure rather than a choice to present.

## Reproducible configuration

- `toolchain.json` owns the Xcode and generator pins.
- `App/Workbench/Package.swift` owns the native deployment minimum.
- `Scripts/app-version.sh` derives the app's version and build from git, and `App/project.yml` owns its copyright.
- `ProfileFile` owns the exported profile's type identifier and file extension.
- `WorkbenchWindows` owns the windows' identifiers and titles.
- `FrontPanelDisplayLayout` owns the display's plotted gain range.

`Scripts/app.sh` derives generator environment values from these sources. `NeXTsoundWorkbenchRender --document-type` emits the exported profile's type JSON without creating a window or initializing the rendering application. The generated Xcode project and property lists stay ignored. The generator runs from its packaged executable so its bundled setting presets remain available.

The `NXSUSBHostShim` target links Homebrew's static `libusb` (`brew install libusb`) from `/opt/homebrew`, unlike the checksum-pinned tools above; it is not version-pinned. Homebrew is needed only to build the app. The library is linked into the app executable, the package's command line tools and `picotool`, so the app runs self-contained and loads no library from a directory a user-level process can write. After the Release build, `Scripts/app.sh` runs `Scripts/check-system-libraries.sh`, which fails when any Mach-O file in the bundle loads a library from outside macOS and the bundle. Homebrew on Apple Silicon only ships an arm64 build, so the app targets `ARCHS: arm64` in `App/project.yml` rather than the default universal set.
